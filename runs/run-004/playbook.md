# Run 004 Playbook

Accumulated lessons, added era by era:

1. A support burden is only a candidate wedge after measuring a baseline and identifying a payer.
2. A technical proposal or platform signal does not prove customer adoption.
3. Permissioned, low-friction data collection must help the person doing the work.
4. Separate daily user, buyer, budget authority, and action authority.
5. Use manual prototypes before automation; write kill thresholds before tests.
6. For exceptions, identify who is allowed to authorize the next action.
7. A manual service validates workflow, not software margins; test a second buyer with limited custom effort.
8. Count operator review, correction, security, integration, and support as unit costs.
9. For consequential records, measure completeness separately from material error.
10. Keep evidence preparation distinct from decision or submission authority.
11. Compare against incumbent and native platform capabilities before claiming a gap.
12. Measure an agent and human-review policy as one workflow at buyer-defined reliability and cost targets.
13. An evaluation result has value only if a buyer uses it in a real decision.
14. Payment for an evaluation does not prove repeatable software economics; require paid reuse.
15. Keep forecast counterforces explicit and do not treat earlier forecasts as later-era facts.
